# Slashview provisioning (review only)
1. In Cloudflare create a dedicated D1 database named slashview-auth. Do not reuse any Slashpromo or Slashcure binding. Copy wrangler.example.toml to an untracked wrangler.toml, insert the database ID, apply schema.sql to the dedicated database, and verify staging first.
2. Deploy a separate Worker with REGISTRATION_ENABLED unset. Use a staging hostname; keep production registration disabled. Set any operator token through Worker secrets, never through source, chat, APK or browser storage. Do not expose the review dashboard publicly. Establish Cloudflare Access with owner-only identity and MFA before enabling admin routes; validate Access JWT at the Worker and replace interim shared token authentication.
3. In Google Cloud create a dedicated OAuth project for Slashview, configure branding and support email slashviewofficial@gmail.com, create Android and web OAuth clients. Android package remains com.slashpromo.app; obtain actual SHA-1 from verified production signing certificate (not SHA-256). Configure debug separately. Server validates Google ID token audience, signature, issuer, expiry and one-time nonce; no automatic email-only account linking. Client IDs are public configuration, secrets are not.
4. Select transactional email provider and verified sending identity. Support Gmail address is not automatically a verified transactional sender. Do not embed mailbox passwords or API keys. Implement hashed, single-use expiring verification/reset tokens, generic responses, throttling, and session revocation after password reset. Verify actual delivery and abuse limits before activation.
5. Finalize and publish privacy/terms, configure owner access and recovery, test registration, Google sign-in, approval, calendar trial, subscriptions, device limits, offline license and local data preservation. No production registration or mandatory login until all gates pass.
6. Keep WhatsApp excluded. Do not activate paid services without owner approval.
